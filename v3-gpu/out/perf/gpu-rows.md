# M6b (preliminary): SVG vs GPU rows

SVG (v2 page as is) against the GPU page (M3 live adapter: v2 runtime verbatim → slot `innerHTML` intercepted →
parse/tessellate → WebGPU redraw of the whole figure each frame). Native-rotor rows (M5) come later.

Generated by `node bench/run-gpu-rows.mjs` (`--report-only` rebuilds only the table between the markers; the prose
is hand-written). Median of 3 runs (headed: 1), fresh Chrome per run, SVG and GPU runs of one page back to back with
the order alternating per repeat; each run waits for ≥ 50 % machine idle and is discarded below 25 %. Chrome
154.0.8037.99, Apple M4 Pro (ANGLE Metal / Graphite for SVG, Dawn Metal for WebGPU), macOS 27.2. Other agents (an M3
QA Chrome) ran on the machine throughout: machine-wide GPU utilisation before a run was 0–47 %.

Pages (all light theme):
- **centrifuge/svg** = `bench/v2/centrifuge-light.html` (frozen v2, sha1 095104dedae6, same as the M6a baselines);
  **centrifuge/gpu** = `bench/gpu/live-light.html` (frozen copy of `out/gpu/live-light.html`, sha1 d1e798e35bb6).
  The GPU page embeds a slightly newer runtime.js (adds the inert `frameOffset` hook for assembly hand-offs);
  identical behaviour for a lone centrifuge.
- **stress10-iframe** = 10 iframes of the page (`node bench/stress.mjs <page> --mode iframe`):
  `bench/stress10-iframe-light.html` / `bench/stress10-iframe-gpu-light.html`. Apples to apples: every GPU iframe is a
  separate document with its own `GPUDevice`, canvas, swap chain and pipelines.
- **stress10-inline/svg** = `bench/stress10-light.html` (M6a inline stress, one document) for reference.

Configs: **desktop** = 1280×900, DPR 2, no throttle; **phone** = 390×844, DPR 3, mobile emulation, 4× CPU throttle
(renderer main thread only: raster workers, GPU process and the GPU itself run at full speed); **headed** = desktop in a
real window on the 144 Hz display (per-frame columns are then per 6.9 ms frame).

## Interpretation

**Single centrifuge (both 60 fps headless, 144 fps headed, ≈ 0 dropped):**
- Renderer main thread: GPU −20 % desktop (2.35 vs 2.94), −22 % phone (8.64 vs 11.08). Style+layout and paint
  practically vanish (phone 2.46 → 0.28 and 2.80 → 0.37), but script grows: +0.62 desktop, +2.24 phone. The adapter's
  parse (3.46 ms phone) costs more than the browser's own innerHTML parse + DOM build it replaces; live-js (3.04 phone)
  equals the M6a frozen floor (2.94), i.e. sim + string building is untouched, as M6a #2 predicted.
- GPU process CPU −73 % (2.96 → 0.81 desktop): Dawn decoding of the WebGPU stream (0.32) is far cheaper than Graphite
  replaying the slot-touched tiles (2.56). Renderer raster workers 0.50 → 0.01.
- GPU hardware: the GPU page adds more machine-wide util than SVG (+21 vs +12 points desktop, +21 vs +8 phone) and its
  pass is 4.2–4.7 ms (2.9 ms headed, higher clocks). The pass time does not scale with canvas pixels (0.13–2 MP all
  ≈ 4–5 ms): the cost is per-frame geometry, not fill (see findings).

**Stress ×10 desktop: no fps change (43.7 SVG vs 43.0 GPU, ≈ 27 % dropped), but a different bottleneck.**
Main thread −27 % (22.9 → 16.9 ms) and GPU-process CPU −88 % (19.3 → 2.3 ms), yet the GPU is saturated (util 100 %
vs 79 % for SVG) and CrGpuMain sits 21.6 ms/frame in `WaitForCommandsToBeScheduled::Dawn`: the GPU page is bound by
GPU hardware (10 full-scene redraws per frame, ≈ 2.3 ms each at full clocks = 43 fps), SVG by main thread + Graphite
CPU. Headed confirms it (both ≈ 43 fps, p50 20.9 ms = 3 vsyncs at 144 Hz).

**Stress ×10 phone (4×): GPU 13.2 fps vs SVG 10.7 (iframe) / 12.7 (inline).** Main thread −19 % (94.3 → 76.4 ms), all
of it from style/layout/paint (−42 ms) partly eaten by script (+26 ms: parse 35 ms/frame, encode 5.7). Still
main-thread bound far below 60 fps; even with a free CPU the GPU would cap it near 24 fps (Σ pass 41.6 ms at
uncontended ≈ 4 ms each).

**iframe vs inline SVG:** separate documents cost ≈ 10–15 % more (desktop 43.7 vs 47.9 fps, phone 10.7 vs 12.7;
per-document style/layout/paint overhead). Compare GPU iframe rows with SVG iframe rows.

**Where the GPU path wins / loses (adapter path, today):** wins everything the browser did after the string
(style/layout/paint/raster/GPU-process CPU, ≈ −90 %), loses on JS parse (adapter > innerHTML) and on GPU hardware
(full redraw every frame vs SVG's damaged tiles). Net: a modest main-thread win, no frame-rate win on desktop, +20 %
fps on the throttled phone stress. The main-thread prize is live-js + parse (≈ 6.5 ms/instance phone) → native rotor
(M5); the GPU prize is not redrawing the static scene.

## Findings

1. **10 GPUDevices in one page work**: 10/10 ready, one adapter, no device loss or console problems in 14 GPU-page runs;
   ready 0.34–0.45 s after load desktop, 1.8–2.0 s phone (4× main thread; boot is serialized on the shared renderer
   main thread). No limit hit, but each device carries its own pipelines, MSAA + depth targets and swap chain, and the
   10 command streams contend on the GPU with no coordination → a production page must share one device (and
   ideally one canvas/pass) across figures.
2. **The GPU renderer's per-frame GPU cost (~2.3–4 ms per centrifuge, resolution-independent) is the new desktop
   bottleneck.** `src/renderer.ts` re-renders the whole static scene every frame (21,050 stroke segments as instanced
   quads + 72,864 fill vertices, 33 draws, 4× MSAA); `strokeShade` (src/shaders.ts) loops over ±3 neighbour segments
   with storage-buffer reads per fragment and `discard`s (defeats early-Z / HSR on Apple TBDR). Since time does not
   fall with pixels, suspect vertex/tiler or per-segment work first; confirm with an Xcode Metal System Trace before
   optimising. Candidates: cache the static scene (render static spans between slot ranks once into textures, redraw
   only slots), skip frames whose slots did not change (already: unchanged writes are skipped, but a frame with any
   change redraws all), drop `discard` in favour of alpha 0 with blending.
3. **Adapter parse is costlier than the browser's innerHTML** (3.46 vs ≈ 2 ms phone/instance). The GPU path only
   pays off on the main thread because style/layout/paint go away. A per-element markup cache or the M5 native rotor
   (no strings) is needed for phones (FINDINGS-M3 #4 confirmed at scale: 35 ms/frame for 10 instances).
4. **GPU timestamp pass times are not comparable across loads**: 4.1 ms alone, 2.8–3.0 with a second instance
   (DVFS clocks up), 16 ms each with 10 contending devices. Use Σ pass only uncontended (phone stress, CPU-bound) and
   machine util for saturation.
5. Minor (GPU page): on the phone stress each instance draws ≈ 1.03× per frame (10.29 draws/frame for 10 instances),
   i.e. a few frames get a second full redraw (a pending `request()` rAF draw on top of the slot-change microtask
   draw?). Worth a look since a redraw is the expensive part.
6. v2/kit: nothing new beyond FINDINGS-M6a; the GPU build carries a newer runtime.js than the frozen v2 centrifuge
   page (frameOffset), harmless here but `bench/v2` should be refreshed together with `bench/gpu` when v2 changes.

## Tooling notes / caveats

- `tools/perf.mjs` (backwards compatible): `--trace-category` (extra categories), `--gpu-util` (ioreg sampler),
  `--gpu-ready-timeout` (waits until every frame's `__gpu` is ready/failed before warmup; no-op on SVG pages);
  `gpuPage` section (instances, adapter(s), readiness, draws/frame, frameStats per instance incl. segment/vertex
  counts, Σ medians); trace adds `webgpuMs`, `gpuWaitMs`, `gpuCpuMs`.
- **Bug fixed in perf.mjs**: with iframes, page rAF timestamps are on each document's timeline, so every iframe's
  callbacks counted as separate frames (page-frame ratio 1000 %, per-frame callback stats wrong; rAF cb sum was
  right). Timestamps are now shifted by `performance.timeOrigin` and snapped to the top loop's frame. Single-document
  pages are unaffected (no M6a numbers change).
- **rAF cb under-reports GPU pages**: the adapter flush (parse/upload/encode/draw) runs in a microtask after the
  runtime's rAF callback returns, outside the wrapped callback. Use script (CDP) or the live-js/parse/upload/encode
  sums. Hence rAF cb is not in this table.
- `__gpu.frameStats()` medians are quantised to 0.1 ms (performance.now is coarsened to 100 µs without
  cross-origin isolation); the preload's sums average this out, so the table uses sums for CPU and frameStats only for
  the GPU pass.
- GPU total for the GPU page is dominated by the wait under saturation; compare **GPU-proc CPU** (or GPU raster vs
  WebGPU decode) for CPU cost and **GPU util / GPU pass** for hardware load.
- The `disabled-by-default-gpu.dawn` category is optional: `WebGPU` events (always on) already contain 97 % of the
  decoder time (HandleDawnCommands always nests inside).
- Raw runs: `out/perf/m6b/*.json`, log `out/perf/m6b/run.log`, per-run values `out/perf/gpu-rows.json`; scaling
  pages `bench/stress{1,2,5}-iframe-gpu-light.html`.
